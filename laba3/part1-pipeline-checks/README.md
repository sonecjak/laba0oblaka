# Лаба 3 — CI/CD

## Часть 1. Плохой пайплайн и проверки кода

Работаем с сервисом «Заметки» из `laba0` (Flask + PostgreSQL).

### Что добавлено

| Файл | Зачем |
|---|---|
| `.github/workflows/bad-ci.yml` | плохой пайплайн, сохранён для сравнения (запускается вручную) |
| `.github/workflows/ci.yml` | хороший пайплайн: `lint → test` |
| `laba3/part1-pipeline-checks/requirements-dev.txt` | Flask, psycopg2, pytest и ruff с зафиксированными версиями |
| `laba3/part1-pipeline-checks/pyproject.toml` | настройки ruff и pytest |
| `laba3/part1-pipeline-checks/tests/` | 17 тестов API |

Файлы пайплайнов лежат в `.github/workflows/` в корне: GitHub запускает только их оттуда. Код сервиса в `laba0` не меняли, тесты подключают его из `../../laba0/backend`.

### Проверки

**Lint — ruff.** Включены правила: стиль (E, W), ошибки вроде неиспользуемых импортов и опечаток в именах (F), порядок импортов (I), типичные баги (B), устаревший синтаксис (UP).

**Тесты — pytest.** `app.py` при импорте сразу подключается к базе, поэтому тесты идут против настоящего PostgreSQL: в CI его поднимает service-контейнер `postgres:16.14-alpine`. Что проверяем:

- `/` отдаёт фронтенд, `/api/health` ходит в БД и отвечает `ok`, у каждого ответа есть заголовок `X-Backend-Id`;
- заметка сохраняется в базу, пробелы по краям обрезаются, новые идут первыми;
- пустой текст, одни пробелы, число, `null`, отсутствие поля, массив, не-JSON и текст длиннее 1000 символов дают `400`, и в базу ничего не попадает;
- если база недоступна, API отвечает `503`, а не падает.

Запуск локально:

```bash
cd laba0
docker compose up -d
cd ../laba3/part1-pipeline-checks
python3 -m venv venv
source venv/bin/activate
pip install -r requirements-dev.txt
ruff check --config pyproject.toml ../../laba0/backend tests
pytest
```

### Плохие практики и их исправления

| № | Плохо (`bad-ci.yml`) | Чем опасно | Хорошо (`ci.yml`) |
|---|---|---|---|
| 1 | `actions/checkout@main`, `actions/setup-python@main` | код экшена меняется без нашего ведома: сборка может сломаться сама или выполнить чужой изменённый код | экшены закреплены по SHA коммита с комментарием версии: `@3d3c42e…  # v7.0.1` |
| 2 | `postgres:latest`, `python-version: "3.x"`, `ubuntu-latest`, `pip install flask pytest ruff` без версий | сегодня зелёный, завтра красный без единого изменения в коде; прогоны невоспроизводимы | `postgres:16.14-alpine`, Python `3.13`, `ubuntu-24.04`, версии всех пакетов в `requirements-dev.txt` |
| 3 | нет кеша, все пакеты качаются заново на каждый прогон | медленно, лишний трафик | `cache: pip` в `setup-python`, ключ кеша считается от `requirements-dev.txt` |
| 4 | `ruff check … \|\| true` и `continue-on-error: true` у тестов | **пайплайн зелёный при сломанном коде** — проверки есть только для вида | никаких `\|\| true`: любая ошибка линтера или теста валит прогон |
| 5 | у БД нет healthcheck | тесты могут стартовать раньше, чем база готова, отсюда случайные падения | `pg_isready` в `options`: шаги начинаются только когда БД принимает подключения |
| 6 | нет блока `permissions` | токен `GITHUB_TOKEN` получает права по умолчанию, шире нужного | `permissions: contents: read` |
| 7 | всё в одной задаче, нет таймаута, запуск без фильтров | непонятно, что именно упало; зависший прогон может висеть часами | две задачи `lint` и `test` (`test` ждёт `lint` через `needs`), `timeout-minutes`, запуск только при изменениях в `laba0/` или в папке пункта, `concurrency` отменяет устаревшие прогоны |

### Остановка пайплайна при ошибке

`test` объявлен с `needs: lint`. Если линтер нашёл ошибку, задача `lint` красная, `test` помечается как пропущенная (skipped), прогон целиком красный. Если упал хотя бы один тест, красный тоже. Отчёт pytest сохраняется артефактом `pytest-report` даже при падении.

### Красный и зелёный прогоны

1. Красный: в начало `laba0/backend/app.py` добавили неиспользуемый импорт `import json` (перед `import os`), закоммитили, запушили.
   Результат: `Lint (ruff)` упал с `F401 'json' imported but unused`, `Tests` не запускались.

   _скрин красного прогона_

2. Зелёный: убрали импорт, закоммитили, запушили. Обе задачи зелёные.

   _скрин зелёного прогона_

3. Для сравнения запустили `BAD CI` вручную на красном коммите — он **зелёный**, хотя линтер ругается (ошибку видно только если открыть лог шага).

   _скрин зелёного BAD CI с ошибкой в логе_

### Передача следующему участнику

Хороший пайплайн готов к добавлению стадий: новая задача пишется в `jobs:` файла `.github/workflows/ci.yml` с `needs: test`, тогда она запустится только после зелёных проверок. Правила, которых держимся: экшены по SHA, образы и пакеты с версиями, `timeout-minutes` у каждой задачи, без `|| true`.
